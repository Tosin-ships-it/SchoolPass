# RULES_ARRIVAL.md

## Job
Hold the arrival window, manual code rate limit, code validity window, and code scope rules.

## Rule 1. Code ownership
The QR code and the manual code are generated and displayed by Staff through the Staff and Admin Interface, at the school's arrival point.
The code is not sent to individual parents.
Reason: a code sent to a parent can be shared with anyone. A code at the gate is only useful to someone at the gate.

## Rule 2. Code scope
A code is scoped to one school and one school day.
The code is not valid on any other day or at any other school.
Reason: scoping limits how far a leaked code can travel.

## Rule 3. Server decides validity
The client sends the code to the server.
The server decides whether the code is valid.
The client never decides validity on its own.
Reason: a client decision can be reversed by a modified client.

## Rule 4. Arrival window
Confirm Arrival is accepted only inside the configured arrival window.
Current setting: 6:30 AM to 10:00 AM on a configured school day (PRD Section 11.2, Section 17).
Reason: a window limits when a confirmation can be created.

## Rule 5. Code validity window
The code expires at the end of the configured arrival window (10:00 AM).
The code cannot be used after the window.
Reason: an expired code does not prove the child arrived today.

## Rule 6. Manual code rate limit
Repeated invalid manual code attempts are rate-limited per parent session.
Current setting: 5 attempts per parent session per 15 minutes (PRD Section 11.8, Section 17).
Reason: an unthrottled code entry can be guessed.

## Rule 7. Duplicate prevention
The `ArrivalConfirmation` table has a unique constraint on student and date.
A second attempt returns the existing record.
No new record is created.
Reason: one confirmation per student per day.

## Rule 8. Non-school day
On a weekend, holiday, or any day not configured as a school day, Confirm Arrival is disabled.
No code is generated for that day.
The parent sees the message in `RULES_ERROR_STATES.md`.
Reason: there is no arrival to confirm on a day the school is closed.

## Rule 9. Parent-to-student check
The server verifies the `ParentStudent` link before creating a confirmation.
The child selector in the UI is a convenience, not the check.
See `RULES_AUTH.md` Rule 2.
Reason: a valid code plus another parent's child is still not the parent's child.

## Rule 10. Every attempt is logged
Every confirmation attempt is logged, successful or not.
Reason: the log is how the school investigates a dispute about arrival.

## Rule 11. Code generation
The QR code value is a random string of at least 128 bits, generated by the server.
The QR image is generated client-side from that string.
The manual code is six digits, generated by the server, unique within the school day.
Reason: random values cannot be guessed from a pattern.

## Rule 12. Time zone
All timestamps use the school's configured time zone.
The default is Africa/Lagos.
Reason: a local time avoids confusion about when the window closes.

## Rule 13. Code regeneration
If Staff regenerate the daily code mid-window, the previous code stops validating immediately.
Reason: a regenerated code exists because the old one must not be used.
